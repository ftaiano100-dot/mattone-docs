<Warning>
**Questa pagina NON è più l'architettura di riferimento.**

Per collegare un nuovo PMS o una nuova capability all'AI Ospiti, il modello corretto è il **gateway multi-tenant** `mcp.mattone.co`: [Gateway multi-tenant](/internal/conduit-knowhow/gateway-multi-tenant).

`cosmica-booking` resta qui come **precedente storico** e come descrizione di **cosa gira oggi per Cosmica** (che è un tenant singolo e ci resta). Non copiarlo per uno studente nuovo.
</Warning>

## Cosa è, davvero

Il repo `~/Projects/cosmica-booking` (Next.js su Vercel, dominio `stay.cosmicarentals.com`) ospita gli endpoint che Conduit chiama come custom tool **per Cosmica**:

```
src/app/api/mcp/
  krossbooking/route.ts    ← portale + check-in + disponibilità (Kross, chiave OWN Cosmica)
  hostaway/route.ts        ← PMS Hostaway (Dubai + Casa Dora/Museo)
  shelly/route.ts          ← apertura porta / stato dispositivi smart-home
```

Ogni `route.ts` definisce un array `TOOLS` (`name` / `description` / `inputSchema`) e un dispatcher che risponde JSON. La skill operativa che descrive come Conduit li interroga è `smart-checkin-mcp`.

## Perché non è il template per gli studenti

Il difetto è strutturale, non stilistico:

| | `cosmica-booking` | Gateway `mcp.mattone.co` |
|---|---|---|
| Tenant per deploy | **1** | **N** |
| Credenziali PMS | env var del progetto | Vault Supabase, per-tenant |
| Nuovo cliente | nuovo deploy + nuovo dominio + nuove env | riga DB + secret nel Vault |
| Identificazione tenant | implicita (è il deploy) | header `X-Student-Token` |
| Sospensione per morosità | da costruire ogni volta | `isTenantSuspended` centralizzata |

Replicare questo pattern per-studente significa moltiplicare deploy, domini e superficie di segreti. Il gateway esiste esattamente per non farlo.

<Warning>
**Precedente di sicurezza da non ripetere.** Gli endpoint `/api/mcp/*` di `cosmica-booking` sono nati **senza auth guard**: chi conosce l'URL ottiene PII ospiti (nome, email, telefono, portal URL, chi è in casa). Tollerabile-ish per un singolo workspace interno; **replicarlo per-studente esporrebbe i dati ospiti di ogni PM su un URL indovinabile**. Nel modello multi-tenant l'identificazione del tenant è obbligatoria per costruzione (`X-Student-Token`), e questo è uno dei motivi per cui esiste.
</Warning>

## Cosa resta valido di questo repo

Due cose, e vanno tenute distinte dal layer tool-Conduit:

1. **La logica di dominio.** La logica "ricca" Kross del gateway (`lib/kross-mcp.js`) è un **port fedele** di quella di `cosmica-booking`, parametrizzata su una funzione `call(action, body)` legata al token dello studente invece che su una chiave hard-coded. Il comportamento dei tool è lo stesso; a cambiare è **da dove arrivano le credenziali**.
2. **Il template del Direct Booking site.** Per il **sito di prenotazione diretta** di un PM, `cosmica-booking` resta il template canonico da forkare: lì il modello single-tenant è corretto (un sito, un brand, un dominio per PM). Questo non è in discussione, e non va confuso col layer dei tool Conduit.
