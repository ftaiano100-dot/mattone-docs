## L'idea in una riga

**Un solo deploy serve N studenti.** Conduit non conosce le credenziali del PMS: manda un **token opaco** che identifica il tenant, e il gateway risolve la terna di quel tenant dal **Vault Supabase** al momento della chiamata.

```
Workspace Conduit studente A ─┐
Workspace Conduit studente B ─┼──▶  mcp.mattone.co  ──▶ Vault Supabase (credenziali per-tenant)
Workspace Conduit studente C ─┘     (1 deploy Vercel)         │
                                            │                 ▼
                                            └────────▶  PMS DI QUELLO STUDENTE
```

Il token viaggia nell'header **`X-Student-Token`**. Non c'è nessun segreto del PMS nella dashboard Conduit, in nessun workspace.

## Il contratto HTTP (verificato in esecuzione)

Ci sono **due superfici**, e non sono intercambiabili.

### 1. `POST /api/mcp/<capability>` — MCP JSON-RPC (quella che usa Conduit)

È il percorso reale dei custom tool. Body JSON-RPC standard, header `X-Student-Token`.

```
POST https://mcp.mattone.co/api/mcp/krossbooking
X-Student-Token: <token del tenant>
Content-Type: application/json

{ "jsonrpc": "2.0", "id": 1, "method": "tools/call",
  "params": { "name": "get_in_house_guests", "arguments": {} } }
```

Capability oggi in produzione: `krossbooking`, `shelly`, `stripe` (un file per capability sotto `api/mcp/`).

### 2. `POST /api/kross` — passthrough a "azione"

Superficie più semplice e più vecchia (`{ "action": "...", "payload": {} }`, stesso header). Utile per script e diagnostica, **non** è quella su cui girano i custom tool Conduit.

### Health

`GET /api/ping` → `{"ping":"ok"}`.

<Note>
**Il routing è quello di Vercel: le function stanno sotto `/api/...`.** Un path tipo `/kross/<action>` non esiste (risponde 404). Verificato il 2026-08-22:

| Chiamata | Risposta reale |
|---|---|
| `GET /api/ping` | `200` · `{"ping":"ok"}` |
| `POST /api/mcp/krossbooking` `tools/list` | `200` · JSON-RPC con 8 tool |
| `POST /api/kross` senza header | `401` · `{"error":"Manca X-Student-Token"}` |
| `GET /kross/ping` | `404` |
</Note>

## Come il gateway risolve il tenant

Tutto sta in `lib/vault.js`. Il gateway **non** usa la service-role: usa la **ANON key** più una RPC protetta da un **secret condiviso** (`GATEWAY_SHARED_SECRET`), così una chiave rubata dal front non apre il Vault.

| Capability | Funzione | Come trova il segreto |
|---|---|---|
| KrossBooking | `resolveTerna(token)` | RPC `gateway_resolve_kross_terna(p_token, gw_secret)` → risolve via **`pms_integrations.cred_secret_id`** (il link canonico scritto dall'admin UI). Fallback legacy: secret nominato `kross_terna_<token>` |
| Shelly | `resolveShellyConfig(token)` | RPC `get_vault_secret` sul nome `shelly_config_<token>` |
| Stripe | `resolveStripeKey(token)` | RPC `get_vault_secret` sul nome `stripe_key_<token>` |
| Manopole non segrete | `resolveStudentConfig(token)` | `student_config_<token>`; ritorna `{}` se assente (non lancia) |

<Warning>
**Due trappole documentate male altrove**, entrambe verificate leggendo il codice:

1. **Non è `SUPABASE_SERVICE_KEY`.** `lib/vault.js` usa `SUPABASE_URL` + `SUPABASE_ANON_KEY` + `GATEWAY_SHARED_SECRET`, nonostante README e `.env.example` del repo citino ancora la service key. **Il codice è la specifica, i suoi docs sono stale.**
2. **La terna Kross NON si cerca per nome `kross_terna_<token>`.** L'admin UI salva il secret con un nome randomico e lo collega **solo** via `cred_secret_id`: il lookup per nome non lo trova mai e produce il falso negativo "Terna non trovata". Il path canonico è la RPC `gateway_resolve_kross_terna`. Il lookup per nome sopravvive **solo** come fallback per gli slug storici.
</Warning>

## Due modelli di token (entrambi vivi)

| Modello | `X-Student-Token` | Risoluzione | Esempio |
|---|---|---|---|
| **v2 canonico** | `pms_integrations.id` (uuid) | `cred_secret_id` via RPC | Solisera, SevenHome, MBA Prime |
| **v1 legacy** | slug (`hostmanager`, ...) | secret per nome `kross_terna_<slug>` | Host Manager (tool ancora su slug) |

Modello corretto verso cui convergere: **tutti su `mcp.mattone.co`, token = uuid canonico**; l'unica differenza tra un partner e un "own" è **quale api_key sta nella terna** (generica partner vs propria), perché il gateway fa `terna.api_key || getPartnerApiKey()`.

<Warning>
**Prima di cancellare un secret `kross_terna_*` dal Vault**: "0 riferimenti in `pms_integrations.cred_secret_id`" **non** significa eliminabile. Un tenant può ancora usarlo via **slug** dal fallback per-nome, perché i custom tool Conduit hardcodano l'header. Va controllata **anche** la lista dei custom tool del workspace Conduit, non solo i link a DB.
</Warning>

## Cosa il gateway dà gratis a ogni nuova capability

Chi aggiunge un PMS non riscrive queste cose: le eredita.

- **Isolamento tenant**: le credenziali non stanno mai in Conduit né in una env var per-cliente.
- **Un solo deploy**: nuovo studente = riga in `pms_integrations` + secret nel Vault. Zero deploy, zero dominio nuovo.
- **Dunning (G7)**: `isTenantSuspended(token)` viene chiamata in `tools/call` **prima** di eseguire; se il tenant è sospeso l'agente riceve un errore pulito invece di dati. Fail-**safe**: se l'RPC va in errore la funzione ritorna `false`, per non abbattere i tool di tutti su un problema transitorio del DB.
- **Errori applicativi come contenuto**: un fallimento del PMS torna come `result.content` con `isError: true`, non come 500 — così l'agente lo legge e lo spiega all'ospite.

## Invariante di verifica (non barare sul self-test)

<Warning>
**`tools/list` NON prova che un tenant funzioni.** Nel codice il ramo `tools/list` risponde **senza leggere il token e senza toccare il Vault**: passa anche per un tenant le cui credenziali non sono risolvibili. È esattamente il buco che ha prodotto integrazioni verdi lato admin e "Terna non trovata" a runtime.

Per certificare un tenant `connected` serve un **`tools/call` read-only sul gateway reale**, con l'`X-Student-Token` vero. Stessa regola per ogni nuova capability, ImmobiNet compresa.
</Warning>

Vale anche la versione generale: **un health-check lato admin che valida le credenziali non prova che il path runtime del gateway funzioni.** Sono due percorsi di codice diversi.

## Quando NON passare dal gateway

Il gateway serve i **tenant studenti**. Non tutto ci passa, e va bene così:

- **Cosmica Italia / Cosmica Dubai** usano il connettore nativo Conduit e i propri endpoint su `stay.cosmicarentals.com`, **senza** `X-Student-Token`.
- Un PM con **chiave Kross propria** su connettore nativo Conduit non tocca il gateway: un "Terna non trovata" per uno di questi è **corretto**, non un bug. (Eccezione storica: Solisera è un "own" che passa comunque dal gateway, con la propria api_key dentro la terna.)
- Il **revenue/prenotazioni** letto da `mattone-platform` usa il client REST diretto con le credenziali per-studente da `pms_integrations`, **non** il gateway: quello serve al provisioning e ai tool Conduit.

## Aggiungere un PMS nuovo: la checklist

Il pattern è **additivo** e ricalcato su `api/mcp/shelly.js`, che è il template più pulito (config-object, senza terna+apikey):

1. `lib/vault.js` → `resolve<Pms>Creds(token)` sul nome `<pms>_creds_<token>` (convenzione di `shelly_config_` / `stripe_key_`).
2. `lib/<pms>.js` → client del PMS, **con le credenziali passate come parametro**, mai lette da `process.env` (è quello che rende multi-tenant il modulo).
3. `lib/<pms>-mcp.js` → `<PMS>_TOOLS` + `handle<Pms>Tool(cfg, name, args)`, stessa forma di `lib/shelly-mcp.js`.
4. `api/mcp/<pms>.js` → copia di `api/mcp/shelly.js` con i due import cambiati.
5. Registrazione del custom tool in **dashboard Conduit** (URL + header `X-Student-Token`): resta un passo manuale, i custom tool non sono creabili via MCP/API.
6. **Self-test runtime** con un `tools/call` read-only prima di dichiarare `connected`.

<Tip>
**Tieni i nomi dei tool identici a quelli Kross** (`check_availability`, `get_reservation_status`, `get_in_house_guests`, `get_upcoming_checkins`, ...). Non è estetica: rende le Skill e il prompting dell'agente **portabili tra PMS** senza riscrivere le procedure quando uno studente cambia gestionale.
</Tip>
