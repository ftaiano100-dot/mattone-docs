## Il fatto

Tre custom tool del workspace Soliséra (`open-door`, `check-device-status`, `get-access-link`) chiamano il proxy SwitchBot `https://solisera-checkin.vercel.app/api/mcp/switchbot`.

Dal **29/05/2026**, data della loro creazione, hanno restituito la stringa `"Error"` **al 100% delle chiamate**. Nessuno se ne è accorto fino all'audit del 22/08/2026: tre mesi.

## La causa: tre mismatch indipendenti

I tool erano scritti per un server MCP che parla `tools/call`. Il server è invece un **JSON-RPC piatto**, con nomi di metodo diretti e una forma di risposta diversa.

| | Cosa manda il tool | Cosa vuole il server |
|---|---|---|
| **Metodo** | `"tools/call"` con il nome dentro `params.name` | `"check_device_status"` direttamente come `method` |
| **Parametro** | `params.arguments.property` | `params.slug` |
| **Risposta letta** | `result.content[0].text` | `result` è un **oggetto piano**, nessun array `content[]` |

Tre errori indipendenti: anche correggendone uno solo, il tool avrebbe continuato a fallire. E ognuno dei tre è invisibile leggendo soltanto il codice del tool: sembrano tutti perfettamente sensati.

<Note>
Riferimento del server reale: `~/Projects/solisera-checkin/src/app/api/mcp/switchbot/route.ts`, dove `rpcOk(id, obj)` restituisce `result` come oggetto piano. I metodi esposti sono `open_door`, `check_device_status`, `get_access_link`, `list_properties`, `get_offline_devices`.
</Note>

## Perché nessuno se ne è accorto

Tre ragioni che si sommano, e valgono per qualsiasi tool nuovo:

<Steps>
  <Step title="Il fallback nascondeva l'errore">
    Il codice leggeva `d.result?.content?.[0]?.text || "Error"`. Poiché `result` era un oggetto piano, `content[0].text` era sempre `undefined` e il tool restituiva sempre `"Error"`. All'agente arrivava una stringa generica, non un fallimento: nessun `isError`, nessuna escalation, nessun allarme.
  </Step>
  <Step title="Nessuno aveva testato l'happy path alla creazione">
    Il tool era stato scritto e salvato, non eseguito. Una singola chiamata a `run_custom_tool` con uno slug reale, il giorno della creazione, avrebbe chiuso il caso in trenta secondi.
  </Step>
  <Step title="Il server stava dicendo la verità e nessuno la leggeva">
    La risposta reale del server era: `Method "tools/call" non supportato. Metodi disponibili: open_door, check_device_status, get_access_link, list_properties, get_offline_devices`. Un messaggio d'errore perfetto, sprecato per tre mesi perché il `|| "Error"` lo buttava via prima che qualcuno potesse vederlo.
  </Step>
</Steps>

## La trappola vera: due proxy dello stesso gruppo, protocolli diversi

Il proxy Shelly di Cosmica Italia, `https://stay.cosmicarentals.com/api/mcp/shelly`, **parla `tools/call`** e funziona (verificato: `casa-gatto` restituisce "Casa Gatto: ONLINE"). Il proxy SwitchBot di Soliséra no.

<Warning>
**Due proxy smart-home costruiti dallo stesso gruppo non condividono necessariamente il protocollo.** I tool di Soliséra erano probabilmente stati derivati per copia da quelli Cosmica, che sono corretti per il *loro* server. Non assumere mai che un secondo tenant, o un secondo servizio, usi lo stesso contratto del primo: **il contratto va riletto sul server, ogni volta.**
</Warning>

## Le lezioni

<CardGroup cols={2}>
  <Card title="Verifica il protocollo PRIMA di scrivere il tool" icon="file-code">
    Apri il codice del server, oppure interrogalo. Il metodo, il nome dei parametri e la forma della risposta sono tre cose distinte e possono divergere indipendentemente.
  </Card>
  <Card title="Testa l'happy path alla creazione" icon="circle-play">
    Un tool salvato e mai eseguito non è un tool consegnato. Su un tool read-only bastano trenta secondi di `run_custom_tool` con un identificatore reale.
  </Card>
  <Card title="Esercita anche il ramo d'errore" icon="bug">
    Il mismatch è emerso solo con un identificatore volutamente inesistente. Un test di solo happy path avrebbe fatto sembrare il problema uno slug sbagliato.
  </Card>
  <Card title="Mai buttare via il messaggio del server" icon="comment-slash">
    Il `|| "Error"` (e a maggior ragione il `|| "<frase affermativa>"`) distrugge la diagnosi alla fonte. Il dettaglio del server va sempre in `rawData.detail`.
  </Card>
</CardGroup>

## Stato

Il 22/08 i 9 tool di Soliséra (6 KrossBooking più i 3 SwitchBot) hanno ricevuto la [guardrail a 6 porte](/internal/troubleshooting/guardrail-6-porte). La guardrail però **non ripara il mismatch di protocollo**: rende il fallimento onesto invece che muto, ma i 3 tool SwitchBot restano non funzionanti finché non si allinea il protocollo.

Il fix richiede una decisione, perché cambia due cose insieme:

- il **body** della richiesta (metodo piatto, `params.slug`) e la **lettura** della risposta (oggetto piano, niente `content[]`);
- una **mappa `property` → `slug`**, perché i tool oggi ricevono dall'agente un nome di proprietà, mentre il server vuole uno slug.

In alternativa si allinea il server al protocollo `tools/call`, uniformandolo al proxy Cosmica. La scelta fra le due strade è aperta.

</Note>
