## Sequenza di setup (canonica per prossimi clienti)

<Steps>
  <Step title="1. Verifica Kross funziona davvero">
    Non bastano le credenziali `connected`: serve il **self-test runtime** (`krossGatewayRuntimeSelfTest`) — controlla che la terna Vault sia leggibile via `kross_partner_read_secret` E che il gateway raggiunga davvero Kross. È stato un fix specifico per non certificare `connected` quando il runtime falliva silente (bug §0 chiuso in `admin/kross/test`).

    ```bash
    curl -X POST /api/admin/kross/test -d '{"id":"<pms_integrations.id>"}'
    ```
  </Step>
  <Step title="2. Provisiona i custom tools">
    In condizioni normali: `POST /api/admin/kross/provision` con `id`, `workspace_id`, `agent_id`, `conduit_token`, `dry_run:true` per vedere il piano, poi `dry_run:false` per applicare.

    <Warning>
    **Aggiornamento 25/08/2026 — il route provision è bloccato**: Conduit ha stretto la validazione Zod su `POST /v1/custom-tools` e richiede `description` obbligatoria per ogni parametro. Il `CONDUIT_CATALOG` in `src/lib/conduit-catalog.ts` definisce i params senza `description` → tutti i tool falliscono `400 ZodError`.

    Fix necessario nel catalog Mattone (vedi §"Bug catalog"). Nel frattempo per HostManager360 i tool sono stati creati **direttamente via Conduit API** con `description` auto-generata (funziona: `enable_globally: true` li rende disponibili a tutti gli agent del workspace, senza bisogno di attach esplicito all'agent).
    </Warning>
  </Step>
  <Step title="3. Verifica agent + tools attivi via API">
    ```bash
    curl -H "Authorization: Bearer $CAPI" \
      "https://api.conduit.ai/v1/agents?workspace_id=$WS"
    # cerca operation_mode ("copilot" | "autopilot"), enabled, triggers, skill_ids

    curl -H "Authorization: Bearer $CAPI" \
      "https://api.conduit.ai/v1/custom-tools?workspace_id=$WS&limit=100"
    # ogni tool deve avere enable_globally:true e parameters con description
    ```
  </Step>
  <Step title="4. Chiedi il numero italiano a Conduit">
    Mail a **Flor Danielle** (`flordanielle@conduit.ai`) — NON a Raniel/Punn (correzione Fra 22/08).

  </Step>
  <Step title="5. Registra WABA nel nostro BM Meta">

  </Step>

## Bug catalog (Mattone)

### Cosa succede
Alla creazione di un custom tool via `POST /v1/custom-tools`, Conduit risponde:

```json
{
  "success": false,
  "error": {
    "issues": [{
      "code": "invalid_type",
      "expected": "string",
      "received": "undefined",
      "path": ["parameters", "date_from", "description"],
      "message": "Required"
    }],
    "name": "ZodError"
  }
}
```

Vale per ogni parametro di ogni tool. È una regressione della validazione Conduit (25/08).

### Riproduzione minima
```bash
# TEST 1 — senza description → 400 ZodError
curl -X POST "https://api.conduit.ai/v1/custom-tools" \
  -H "Authorization: Bearer $CAPI" -H "Content-Type: application/json" \
  -d '{"workspace_id":"...","name":"t1","parameters":{"x":{"type":"string","required":true}}, ...}'

# TEST 2 — con description → passa Zod (poi eventuali errori sul code sono altra cosa)
curl -X POST "https://api.conduit.ai/v1/custom-tools" \
  -H "Authorization: Bearer $CAPI" -H "Content-Type: application/json" \
  -d '{"workspace_id":"...","name":"t2","parameters":{"x":{"type":"string","required":true,"description":"..."}}, ...}'
```

### Fix in `src/lib/conduit-catalog.ts`
Estendere l'interfaccia `ToolParam` con `description: string` obbligatorio, e riempirlo per ogni parametro di ogni tool del catalog (~10-15 tool). Esempio:

```ts
// PRIMA
params: {
  date_from: { type: "string", required: true },
  date_to:   { type: "string", required: true },
}

// DOPO
params: {
  date_from: { type: "string", required: true, description: "Data inizio (YYYY-MM-DD)" },
  date_to:   { type: "string", required: true, description: "Data fine (YYYY-MM-DD)" },
}
```

### Workaround usato per HostManager360
Script standalone che chiama `POST /v1/custom-tools` con `description` auto-generata dai nomi param — bypass del route Mattone. Idempotente (controlla se il tool esiste con `list_custom_tools` prima di crearlo).

Descrizioni riusabili adottate:
- `date_from` → *"Data di inizio del periodo di ricerca (YYYY-MM-DD)"*
- `date_to` → *"Data di fine del periodo di ricerca (YYYY-MM-DD)"*
- `property` → *"Nome o identificativo dell'immobile per filtrare (opzionale)"*
- `guest` → *"Nome dell'ospite per identificare la prenotazione"*
- `reservation_id` → *"ID numerico della prenotazione"*
- `language` → *"Codice lingua ISO 639-1 (default it)"*
- `days_ahead` → *"Numero di giorni in avanti da controllare"*

## Regola nuova: `enable_globally: true` basta

**Non serve attaccare esplicitamente i tool all'agent.** L'endpoint `POST /v1/agents/{id}/tools` che avevamo tentato risponde **404**. La strada corretta: creare i tool con `enable_globally: true` → sono automaticamente disponibili a tutti gli agent del workspace.

Verificabile su un tool esistente:
```bash
curl -H "Authorization: Bearer $CAPI" \
  "https://api.conduit.ai/v1/custom-tools/$TID?workspace_id=$WS"
# → { "enable_globally": true, ... }
```

## Timeout KB Bridge (`sync-knowledge`)

Il route `POST /api/conduit/sync-knowledge` con `commit:true` su un workspace medio-grande (Soliséra, 37 apt) hitta **HTTP 504 dopo 300 sec** — cap Vercel serverless attuale (`maxDuration = 300` nel route).

Fix proposto:
```ts
// src/app/api/conduit/sync-knowledge/route.ts
export const maxDuration = 800; // Vercel Pro + Fluid Compute cap
```

Se il piano Vercel non supporta 800s, il deploy fallirà con errore chiaro — nessun rischio silente. Alternativa: refactoring in chunk (N apt per chiamata + polling client-side).

<Warning>
Il gate template dentro `pushToConduit` (kb-bridge.ts) è hardcoded: se `apt.validation.complete === false` → skip. Fra l'ha messo apposta perché la dedup è create-or-skip per titolo: un push parziale non si aggiorna più a sync successive. Se serve bypass per import "best-effort", va aggiunto un parametro esplicito nel route.
</Warning>

## Listing not mapped (blocker qualità)

Nel pannello **Booking Info** delle conversation Airbnb del workspace HostManager compare:

> "Listing unavailable in Conduit"

Cioè: le prenotazioni Airbnb arrivano (le vede la conversation, la Booking Info ha check-in/check-out), ma il **listing** (l'apt) non è mappato in Conduit. Senza listing associato:
- `check-availability` non sa quale property controllare
- `get-checkin-instructions` non ha `reservation_id` collegato
- Il Copilot genera solo risposte generiche

Fix: automatizzare il mapping listing Airbnb ↔ Conduit ↔ Kross durante il provisioning (come `apartment_registry` per Soliséra, ma su HostManager il flusso è ancora manuale).

## Copilot on-demand vs autopilot

Differenza chiave rispetto a Soliséra:

| | HostManager360 | Soliséra |
|---|---|---|
| `operation_mode` | **`copilot`** | **`autopilot`** |
| Comportamento | Suggerisce, l'operatore approva | Risponde in autonomia agli ospiti |
| Entry point | UI Conduit (⌘+J AI Editor / ⌘+K Operator) | Automatico ad ogni messaggio guest |
| Serve intervento umano | Sì (Gabriele) | No (autopilot pur con guardrails) |

**Il Copilot non appare in automatico nel pannello conversazione** — è on-demand. L'operatore lo attiva con shortcut o pulsante "Compose with AI".

## Cose che NON funzionano (o dove Conduit ti frega)

- **`POST /v1/agents/{id}/tools`** → 404. Non esiste, l'attach lo fai con `enable_globally: true` sul tool.
- **`POST /v1/custom-tools` senza `parameters[].description`** → 400 ZodError (regressione 25/08).
- **`create_custom_tool` payload con `return {...}` diretto invece di `async function main(...)`** → *"Tool code must define the JavaScript entrypoint function named main"*. Entrypoint obbligatorio è `main`.
- **`get_custom_tool` senza `workspace_id`** → 400 Zod "workspace_id required".
- **Endpoint `/v1/workspaces/{id}`** con token partner → error (endpoint workspace-level richiede token owner).
- **`GET /v1/listings`** — non esiste endpoint pubblico REST per listing per workspace. Solo via MCP.
- **REST `/v1/workflows`** → 404. I workflow si toccano solo via MCP Conduit.
