Questo è il pattern che usiamo per impedire a un custom tool di [affermare un fatto falso](/internal/troubleshooting/silent-wrong) su un errore temporaneo. La **specifica di riferimento è il workspace Cosmica Italia**: 9 tool su 10 lo implementano integralmente (il decimo è `stripe-payment-link`, un tool di scrittura, trattato più sotto).

## L'idea

Fra la `fetch` e il `return` ci sono sei modi diversi in cui la risposta può essere inutilizzabile. Vanno controllati **tutti e in quest'ordine**, perché ognuno esclude il successivo: se la `fetch` è esplosa non esiste `r`, se `r` non è ok non ha senso leggere il JSON, se il JSON non parsa non esiste `d`, e così via.

## Le sei porte, in ordine

| # | Porta | Condizione | `reason` | Guarda `isError`? |
|---|---|---|---|---|
| 1 | Rete | `fetch` lancia | `network` | No |
| 2 | HTTP | `!r.ok` | `http:<status>` | No |
| 3 | JSON | `r.json()` lancia | `badjson` | No |
| 4 | **Testo assente** | `text` undefined, null o `""` | `noresult` | **No** |
| 5 | Errore transitorio | `isError` **e** regex transitori | `kb-transient` / `shelly-transient` | Sì |
| 6 | Errore permanente | `isError` non transitorio | `tool-error`, `transient: false` | Sì |

<Warning>
**Le prime quattro porte NON guardano `isError`, ed è il punto centrale del pattern.** Se la `fetch` è fallita, se lo status è 502, se il corpo non è JSON o se il testo non c'è, **non esiste alcun `isError` da leggere**: quel campo vive dentro `d.result`, che in tutti e quattro i casi non è disponibile. Un tool che parte da `if (d.result.isError)` non copre nessuno di questi quattro scenari, e in tre di essi va addirittura in eccezione.
</Warning>

<Warning>
**La trappola della porta 4 è l'errore più comune.** Un errore JSON-RPC top-level ha la forma `{"jsonrpc":"2.0","id":1,"error":{...}}`: c'è `d.error`, **non** c'è `d.result`. Quindi `d.result.content[0].text` è `undefined` e `d.result.isError` è `undefined` (cioè *falsy*, cioè "nessun errore"). Senza la porta 4, un errore di protocollo passa per un successo con testo vuoto, e diventa esattamente il fallback affermativo che stiamo cercando di eliminare. Saltare la porta 4 è il modo più frequente per credere di aver messo la guardrail e non averla messa.
</Warning>

## Cosa deve dire il messaggio BUSY

Il testo restituito all'agente parte da `⚠️ SISTEMA_OCCUPATO` e dice sempre **tre cose**, in quest'ordine:

<Steps>
  <Step title="Cosa NON si sa">
    Formulato come ignoranza, mai come fatto. "Non riesco a verificare lo stato del dispositivo", non "il dispositivo non risponde". "Il calendario è momentaneamente occupato", non "le date risultano occupate".
  </Step>
  <Step title="Cosa l'agente NON deve fare">
    Le tre proibizioni ricorrenti: **mai** usare il calendario nativo di Conduit come ripiego (è inaffidabile sulle date e dice "occupato" su date libere); **mai** inventare dati di accesso, indirizzi o codici porta; **mai** cambiare identificatore per riprovare (nome, email, codice o slug diversi peggiorano il sovraccarico e producono falsi negativi). Su un tool con side-effect si aggiunge la proibizione simmetrica: non dichiarare né riuscita né fallita l'azione.
  </Step>
  <Step title="Cosa fare invece">
    Riprovare **lo stesso identico input** fra circa 30 secondi. E, se persiste, cosa dire all'ospite: che stai controllando, non che il sistema è rotto.
  </Step>
</Steps>

<Tip>
Il messaggio è scritto **per l'LLM, non per l'ospite**. Deve essere esplicito e imperativo, perché è l'unica cosa che l'agente leggerà: le istruzioni negative funzionano molto meglio se sono dentro il risultato del tool che se stanno in una skill lontana nel contesto.
</Tip>

## Snippet riusabile

Questo è il corpo reale di `check-device-status` su Cosmica Italia (v4), la forma canonica da copiare quando si scrive un tool nuovo o se ne hardena uno esistente.

```js Custom tool con guardrail a 6 porte
async function main({ property }) {
  // Regex dei transitori: 429, 5xx, retry esauriti, rate limit, timeout, reset di connessione
  const T = /HTTP\s*(429|5\d\d)|after\s+\d+\s+retries|rate.?limit|too many|time-?d?\s*out|ECONNRESET|ETIMEDOUT|502|503|504|overload/i;

  const BUSY = `⚠️ SISTEMA_OCCUPATO — non riesco a verificare lo stato del dispositivo di "${property}" ora (sistema domotica momentaneamente occupato o irraggiungibile). NON dichiarare il dispositivo offline, rotto o non funzionante: non lo sai. Riprova la STESSA proprietà ("${property}") tra ~30 secondi; se persiste, rassicura l'ospite che stai controllando e riprova a breve.`;

  let r, d;

  // PORTA 1 — la fetch stessa fallisce (DNS, TLS, rete)
  try {
    r = await fetch("https://stay.cosmicarentals.com/api/mcp/shelly", {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({
        jsonrpc: "2.0", id: 1, method: "tools/call",
        params: { name: "check_device_status", arguments: { property } }
      })
    });
  } catch (e) {
    return { message: BUSY, rawData: { property, transient: true, reason: "network" } };
  }

  // PORTA 2 — status HTTP non 2xx
  if (!r.ok) return { message: BUSY, rawData: { property, transient: true, reason: "http:" + r.status } };

  // PORTA 3 — corpo non parsabile come JSON
  try { d = await r.json(); } catch (e) {
    return { message: BUSY, rawData: { property, transient: true, reason: "badjson" } };
  }

  const text = d && d.result && d.result.content && d.result.content[0] && d.result.content[0].text;
  const isError = !!(d && d.result && d.result.isError);

  // PORTA 4 — testo assente o vuoto. Copre il JSON-RPC error top-level: lì d.result NON esiste.
  if (text === undefined || text === null || text === "")
    return { message: BUSY, rawData: { property, transient: true, reason: "noresult" } };

  // PORTA 5 — errore dichiarato E riconosciuto come transitorio
  if (isError && T.test(text))
    return { message: BUSY, rawData: { property, transient: true, reason: "shelly-transient", detail: text } };

  // PORTA 6 — errore dichiarato ma permanente: messaggio specifico, niente BUSY
  if (isError)
    return {
      message: `⚠️ Non riesco a determinare lo stato del dispositivo di "${property}": ${text}. NON inventare lo stato; se serve, verifica il device slug corretto nel blocco Knowledge del listing.`,
      rawData: { property, transient: false, reason: "tool-error", detail: text }
    };

  // Successo
  return { message: text, rawData: { property } };
}
```

### Cosa cambia da tool a tool

Solo tre cose. Tutto il resto è identico e va copiato alla lettera.

- **Il testo di `BUSY`**, adattato al dominio: quale fatto l'agente non deve affermare.
- **La `reason` delle porte 5 e 6**: `kb-transient` per i tool che passano dal PMS, `shelly-transient` per la domotica. Serve solo a leggere i log, ma tenerla coerente aiuta.
- **Il messaggio della porta 6**, che deve suggerire la vera azione correttiva (verificare lo slug, chiedere all'ospite di precisare le date, e così via).

### Varianti per tipo di tool

<AccordionGroup>
  <Accordion title="Tool di lettura (disponibilità, prenotazioni, portali)">
    Il BUSY deve negare esplicitamente la deduzione negativa: "NON dedurre che non ci sia nessun ospite in casa: l'elenco NON è stato recuperato", "NON significa che l'ospite non esista". E deve vietare il ripiego sul calendario nativo Conduit.
  </Accordion>
  <Accordion title="Tool con side-effect (apri porta, pagamenti)">
    Il BUSY deve vietare **entrambe** le affermazioni, non solo quella negativa: "non so se la porta si è aperta: NON dire all'ospite che l'apertura è fallita né che è riuscita". Se ripetere l'azione è innocuo, dillo esplicitamente ("ri-aprire non causa problemi"), altrimenti l'agente non riproverà.

    Hardenare un tool con side-effect cambia **solo il ramo di gestione errori**: la chiamata resta identica, quindi non altera *quando* l'azione avviene. Su Cosmica Italia `open-door` è stato hardenato solo dopo conferma esplicita di Francesco, proprio per questo.
  </Accordion>
  <Accordion title="Tool di scrittura verso terzi (Stripe)">
    Oggi `stripe-payment-link` (Italia) e `generate-stripe-payment-link` (Dubai) **non hanno il pattern** e in più ritornano `{ error: ... }` **senza chiave `message`**, il che viola il contratto di ritorno Conduit (`main` deve tornare un oggetto con `message` stringa). Su errore Stripe il fallimento è a livello di runtime del tool, non un messaggio leggibile dall'agente. Da sistemare: è l'unico buco noto sulla specifica Italia.
  </Accordion>
</AccordionGroup>

<Note>
Il contratto di ritorno è vincolante: `async function main(params)` deve restituire un oggetto con **`message` stringa** e opzionalmente `rawData`. La scrittura via API valida staticamente solo la presenza di `main` e di un `return`; il resto lo scopri a runtime. Usa `list_custom_tool_runtimes` per la firma esatta e i pacchetti disponibili prima di scrivere codice nuovo.
</Note>

## Cosa NON risolve questo pattern

La guardrail nel tool copre gli errori che il sistema a valle **dichiara**. Non copre il caso in cui il sistema a valle risponde 200 con un contenuto sbagliato, che è esattamente il caso Botanique. Per quello la difesa deve stare nel gateway: vedi [Regola d'oro](/internal/troubleshooting/regola-doro-dati-mancanti).
