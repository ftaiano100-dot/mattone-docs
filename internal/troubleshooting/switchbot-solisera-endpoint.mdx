Questa pagina è il riferimento operativo del proxy SwitchBot di Soliséra dopo il fix del **22/08/2026**. Tutto quanto segue è stato verificato **in esecuzione**, non dedotto dal codice. Per la storia di come il problema è nato, vedi [Caso Soliséra SwitchBot](/internal/troubleshooting/caso-solisera-switchbot).

## Un solo endpoint, due hostname

`stay.solisera.it` e `solisera-checkin.vercel.app` **non sono due deploy diversi**: sono due alias dello stesso deployment di produzione del progetto Vercel `solisera-checkin`.

```
$ vercel inspect https://solisera-checkin-csrfvr44q-…vercel.app
  Aliases
    ╶ https://stay.solisera.it
    ╶ https://solisera-checkin.vercel.app
    ╶ https://solisera-checkin-ftaiano100-8216s-projects.vercel.app
    ╶ https://solisera-checkin-git-main-…vercel.app
```

Le due URL rispondono in modo **byte-identico** alla stessa richiesta. Non esiste quindi una versione del route che parla un protocollo e una che ne parla un altro: se un tool fallisce su uno dei due hostname, fallisce anche sull'altro.

<Note>
  Nei custom tool usiamo `https://stay.solisera.it/api/mcp/switchbot`, cioè il dominio di prodotto. È lo stesso dominio che il server restituisce dentro `accessUrl`: se quel dominio cade, cade comunque anche il guest portal, quindi puntarci non aggiunge fragilità.
</Note>

## Il protocollo: JSON-RPC 2.0 piatto, non MCP

Il route `src/app/api/mcp/switchbot/route.ts` **non è un server MCP**, nonostante il path. Il nome del metodo va direttamente in `method`, e l'argomento si chiama `slug`.

| | Corretto | Sbagliato (fallisce sempre) |
|---|---|---|
| Metodo | `"check_device_status"` | `"tools/call"` |
| Parametro | `params.slug` | `params.arguments.property` |
| Risposta | `result` è un **oggetto piano** | `result.content[0].text` |

Metodi esposti: `open_door`, `check_device_status`, `get_access_link`, `list_properties`, `get_offline_devices`, `list_account_devices`.

Autenticazione: header `X-MCP-Token`, confrontato con `MCP_AUTH_TOKEN` su Vercel. Il valore vive **solo** nelle env var Vercel e dentro il `code` dei custom tool Conduit: non va scritto qui né in nessun altro file del repo.

<Warning>
  **`tools/list` non esiste su questo server.** Non puoi enumerare le sue capability con la handshake MCP: il catalogo dei metodi lo ottieni con una `GET` sull'endpoint, che risponde senza autenticazione con l'elenco dei metodi.
</Warning>

## Mappa degli slug

La mappa è **hardcoded** in `src/lib/switchbot.ts` (costante `SWITCHBOT_DEVICES`) del repo `solisera-checkin`: aggiungere una proprietà richiede un deploy, non è una configurazione runtime.

| Slug | Proprietà | Device | Device ID |
|---|---|---|---|
| `urban-beach` | Urban Beach — Solisera | Smart Lock Pro | `DD5763F22B2E` |
| — | (stessa porta, accessorio) | Keypad Touch | `D375103C7761` |
| — | (ponte cloud) | Hub Mini | `DBF232413DB3` |

**`urban-beach` è l'unico slug esistente.** Soliséra ha una sola serratura: l'enumerazione completa dell'account SwitchBot (`list_account_devices`) restituisce tre device, ma uno solo è una serratura. Qualunque altro valore passato come `property` è uno slug sbagliato, non una proprietà non ancora mappata.

## Mappa dei codici d'errore

Verificata chiamando l'endpoint reale, incluso il ramo d'errore.

| Codice | Quando | Come va trattato |
|---|---|---|
| `-32000` | Token errato o assente (**HTTP 401**) | Problema **nostro** di configurazione. Non dire nulla all'ospite sullo stato della porta. |
| `-32001` | Slug sconosciuto su `get_access_link` / `open_door` | Slug sbagliato. **Non riprovare** lo stesso valore. |
| `-32002` | Serratura offline, su `open_door` | Guasto **fisico**. La porta non si è aperta. |
| `-32601` | Metodo non supportato (es. `tools/call`) | Bug di **contratto** nel tool. Va segnalato, non ritentato. |
| `-32602` | `params.slug` mancante | Bug nel tool o slug vuoto. |
| `-32603` | Catch-all della route | **Ambiguo, vedi sotto.** |

<Warning>
  **La trappola del `-32603`.** Su `check_device_status` uno slug sconosciuto **non** arriva come `-32001`: `getDeviceStatus` lancia e finisce nel catch generico della route, quindi arriva come `-32603` con messaggio `Device "…" non registrato`. Classificare il `-32603` come transitorio *soltanto dal codice* manda l'agente in un ciclo di retry infinito su uno slug che non esisterà mai. I tool discriminano quindi anche sul **testo** del messaggio (`non registrat…`) prima di ricadere sul trattamento transitorio.
</Warning>

<Note>
  Tutti gli errori JSON-RPC di questo server tornano con **HTTP 200**, tranne `-32000` che torna 401. Controllare lo status non basta: va sempre letto il corpo.
</Note>

## Come si testa

Il test read-only è `check_device_status`. **Non usare mai `open_door` per verificare**: aprirebbe davvero la porta di un ospite.

<Steps>
  <Step title="Verifica che il server sia vivo">
    ```bash
    curl -s https://stay.solisera.it/api/mcp/switchbot
    ```
    Risponde con `server`, `protocol: "json-rpc-2.0"` e l'elenco dei metodi. Non richiede autenticazione.
  </Step>
  <Step title="Interroga il device con lo slug reale">
    ```bash
    curl -s -X POST https://stay.solisera.it/api/mcp/switchbot \
      -H "Content-Type: application/json" \
      -H "X-MCP-Token: $MCP_AUTH_TOKEN" \
      -d '{"jsonrpc":"2.0","id":1,"method":"check_device_status","params":{"slug":"urban-beach"}}'
    ```
    Usa `urban-beach`, non un nome inventato: uno slug finto esercita solo il ramo d'errore.
  </Step>
  <Step title="Esercita anche il ramo d'errore">
    Ripeti con `"slug":"slug-inesistente-xyz"`. Devi ottenere `Device "…" non registrato`. Un tool che su questo caso risponde "riprova fra 30 secondi" è mal classificato.
  </Step>
  <Step title="Verifica il tool Conduit, non solo l'endpoint">
    Endpoint sano e tool rotto sono compatibili: è esattamente ciò che è successo per tre mesi. Chiudi il giro con `run_custom_tool` su `check-device-status`, workspace Soliséra, parametro `property: "urban-beach"`.
  </Step>
</Steps>

## Problema nostro o problema fisico

È la distinzione che conta davvero in supporto, perché cambia chi deve agire.

| Sintomo | Chi ha il problema | Cosa si fa |
|---|---|---|
| HTTP 401, `-32000` | **Noi** — `MCP_AUTH_TOKEN` disallineato fra Vercel e i tool | Rigenerare il token su Vercel, redeploy, aggiornare i 3 tool |
| `-32601`, `-32602` | **Noi** — contratto del tool sbagliato | Correggere il body del tool |
| `-32001`, o `-32603` con "non registrato" | **Noi** — slug sbagliato nel blocco Knowledge del listing | Correggere il Knowledge, non il tool |
| HTTP 429 / 5xx, timeout, socket | **Transitorio** — non lo sai | Ritentare, senza affermare nulla all'ospite |
| `online: false` con risposta valida | **Fisico, del cliente** | Hub Mini, WiFi o batteria in loco |
| `-32002` su `open_door` | **Fisico, del cliente** | Come sopra: la porta non si è aperta |

<Warning>
  `online: false` **non è un errore del nostro sistema**: è una risposta riuscita che riporta un fatto. Trattarlo come transitorio fa ritentare all'infinito una serratura che nessun retry riporterà online. Trattarlo come colpa nostra manda il team a debuggare il codice mentre l'ospite è chiuso fuori.
</Warning>

## Stato al 22/08/2026

I 3 tool Conduit (`check-device-status`, `get-access-link`, `open-door`) sono stati riallineati al protocollo piatto, mantenendo la [guardrail a 6 porte](/internal/troubleshooting/guardrail-6-porte), e verificati in esecuzione: restituiscono dati reali.

Resta un problema **fisico, lato Cristina**, che nessun intervento software risolve:

```json
{ "online": false, "battery": 0, "lockState": "locked",
  "raw": { "onlineStatus": "offline", "hubDeviceId": "DBF232413DB3" } }
```

La serratura `urban-beach` risulta offline con batteria a 0. Va segnalato alla proprietaria: Hub Mini acceso e LED blu, serratura entro ~5 metri, Cloud Service attivo, batterie sostituite. Finché resta così, l'apertura da remoto non funziona e l'agente deve proporre l'accesso alternativo del listing.
