Questa pagina è il riferimento tecnico del webservice ImmobiNet. Tutto qui deriva dal **reverse engineering del WSDL pubblico** (nessuna doc ufficiale esiste): analisi del 2026-04-23 su ~100KB di XML, più un probe live dell'endpoint il 2026-05-11 (HTTP 401 con envelope parsato correttamente = server vivo, auth check attivo).

## Architettura WSDL

Root: `https://rentallab.immobinet.it/webservice.wsdl`. È un **aggregatore** che importa 5 bundle:

| Bundle | Endpoint SOAP | Scope |
|---|---|---|
| **ModAgenzia** (core) | `/bundle/webservicemodagenzia/service` | Immobili, disponibilità, listini, **prenotazioni**, ricerca |
| **Gruppi** | `/bundle/webservicegruppi/service` | Edifici/residence che raggruppano immobili |
| **ListiniRegole** | `/bundle/webservicemodagenzialistiniregole/service` | Minimum/maximum stay, regole check-in/check-out, aperture |
| **Offerte** | `/bundle/webservicemodagenziaofferte/service` | Sconti, promozioni, offerte 7=6, late booking |
| **Pulizie** | `/bundle/webservicemodagenziapulizie/service` | Prezzi pulizia per immobile/periodo |

<Info>
**Punto risolto**: una prima analisi temeva che il modulo **Prenotazioni** fosse in un bundle esterno non visibile. Il probe live ha confermato che le prenotazioni (`getPrenotazioni`, `setPrenotazione`, `editPrenotazione`, `delPrenotazione`) sono **dentro il bundle pubblico `webservicemodagenzia`**. Questo sblocca il caso d'uso Conduit e Direct Booking: non serve un piano enterprise per leggere le prenotazioni.
</Info>

## Protocollo e autenticazione

- **SOAP 1.1**, `style="document"`, `use="literal"` (document/literal wrapped). Trasporto HTTP/HTTPS.
- Header **`SOAPAction` obbligatorio** per ogni metodo (es. `http://www.immobinet.it/wsdl/WebserviceModAgenziaBundle/getImmobili`).
- Auth = complex type `Auth` nel body di ogni richiesta:

```xml
<imw:auth>
  <core:username>...</core:username>
  <core:password>...</core:password>
</imw:auth>
```

<Warning>
**Namespace gotcha** (imparata durante il probing): lo schema ha `elementFormDefault="qualified"` ovunque, quindi **ogni elemento** vuole il prefisso namespace esplicito. In particolare `<auth>` sta nel namespace del bundle (`imw`), ma i figli `<username>`/`<password>` stanno nel namespace **core**. Sbagliare il prefisso = fault silenzioso.
</Warning>

Username + password in chiaro nel body (mitigato solo da HTTPS). **Nessun token/JWT/OAuth, nessun WSSE, nessun HMAC.** Le credenziali sono spesso le stesse del login web dell'agenzia. Rate limit **non documentato** nel WSDL.

## Convenzioni dati chiave

- **Prezzi in centesimi**: ogni `prezzo` è `xsd:int` = euro × 100 (es. 5,12 € → `512`).
- **Date**: `xsd:date` (YYYY-MM-DD) e `xsd:dateTime` ISO 8601. **Nessun timezone esplicito** → assume `Europe/Rome` lato server.
- **`al` è inclusa**: nel range `dal`/`al`, l'ultimo giorno è compreso (diverso dallo standard ISO/Booking che esclude l'ultimo giorno).
- **Disponibilità = stringa binaria** giornaliera: es. `"1110011"` = 7 giorni, primi 3 liberi, 2 occupati, 2 liberi.

## Le 17 operazioni

### ModAgenzia (core) — 11 operazioni

| Operazione | Tipo | Scopo |
|---|---|---|
| `getImmobili(auth, immobili?)` | READ | Catalogo proprietà con metadati completi (indirizzo, categoria, coords, foto, descrizioni multilingua, composizione, capienza, letti, attributi, CIN, check-in/out) |
| `getDefinizioneAttributi(auth)` | READ | Vocabolario amenities/servizi dell'agenzia (esiste anche `getDefinzioneAttributi`, typo, **deprecated**) |
| `getDisponibilita(auth, anno?, immobili?)` | READ | Disponibilità annuale come stringa binaria per ogni immobile |
| `ricercaDisponibilita(auth, arrivo, partenza, persone, portale?, immobili?)` | READ ★ | Ricerca immobili disponibili per date+persone, **prezzo già calcolato** (con offerte) |
| `getDefinizioneListini(auth)` | READ | Lista rate plan attivi (tipo ∈ giorni/giornaliero/settimanale/periodo/fisso) |
| `getListino(auth, anno, listino?, immobili?)` | READ | Prezzi stagionali dettagliati per rate plan (in centesimi) |
| `getPrenotazioni(auth, dal?, al?, prenotazioni?, immobili?, ultima-modifica?)` | READ ★ | Lista prenotazioni con filtri. `ultima-modifica` = perfetto per **sync incrementale** |
| `setPrenotazione(...)` | WRITE ★ | Crea prenotazione in stato `unpaid` ma **confermata e bloccata** (immobile occupato). Ritorna `id` + `riferimento` |
| `editPrenotazione(auth, id, prezzo?)` | WRITE | Passa da `unpaid` a `paid`. **Aggiorna solo prezzo/stato**, non date/cliente/immobile/note |
| `delPrenotazione(auth, id)` | WRITE | Cancella prenotazione non completata (pagamento fallito) |

★ = metodi centrali per booking flow e Conduit.

### Gruppi — 2 operazioni

- `getGruppi(auth, gruppi?)` — READ: edifici/residence con immobili associati.
- `getAssociazioni(auth)` — READ: mappa gruppo ↔ immobili.

### ListiniRegole — 2 operazioni

- `getListinoRegole(auth, dal, al, listino?, immobili?, portale?)` — READ: min/max stay, `on-arrivo`/`on-partenza` (giorni consentiti check-in/out).
- `getListinoAperture(auth, dal, al, ...)` — READ: aperture/chiusure listino per periodo (`open` bool).

### Offerte — 1 operazione

- `getOfferte(auth)` — READ: sconti/promo. Tipi: `variazione-giorni` (7=6), `variazione-percentuale`, `variazione-fisso`, `fisso` (override totale).

### Pulizie — 1 operazione

- `getListinoPulizie(auth, dal, al, listino?, immobili?)` — READ: prezzo pulizia per immobile/periodo (centesimi).

## Matrice READ/WRITE (la tabella che decide tutto)

| Funzionalità | READ | WRITE | Note |
|---|---|---|---|
| Immobili (metadata) | ✅ `getImmobili` | ❌ | No create/update property via API |
| Attributi/servizi | ✅ `getDefinizioneAttributi` | ❌ | |
| Disponibilità | ✅ `getDisponibilita`, `ricercaDisponibilita` | ⚠️ solo indiretto via `setPrenotazione`/`delPrenotazione` | No block manuale date |
| Listini (prezzi) | ✅ `getDefinizioneListini`, `getListino` | ❌ | **Blocker PriceLabs** |
| Regole soggiorno (MS, CI/CO) | ✅ `getListinoRegole` | ❌ | **Blocker PriceLabs** |
| Aperture/chiusure | ✅ `getListinoAperture` | ❌ | |
| Offerte/sconti | ✅ `getOfferte` | ❌ | |
| Pulizie | ✅ `getListinoPulizie` | ❌ | |
| Gruppi/edifici | ✅ `getGruppi`, `getAssociazioni` | ❌ | |
| Prenotazioni | ✅ `getPrenotazioni` | ✅ `setPrenotazione`, `editPrenotazione`, `delPrenotazione` | **Unica area write completa** |

**Verdetto**: il WSDL è fortemente **READ-biased**. L'unica scrittura è sul ciclo di vita delle prenotazioni. È progettato per un caso d'uso preciso — **sito diretto / channel manager esterno che riserva prezzi in ImmobiNet** — NON per un revenue tool che scrive prezzi. Da qui il blocker PriceLabs (vedi [Hybrid Sync](/internal/immobinet/pricelabs-hybrid-sync)).

## Notifiche PUSH (webhook)

ImmobiNet può inviare notifiche PUSH verso un URL configurato lato agenzia. Ogni evento è una GET/POST con query string:

- `_type` ∈ `removed` | `inserted` | `modified`
- `_event` = entità modificata (es. `ModAgenzia/Prenotazione`, `ModAgenzia/Disponibilita`, `ModAgenziaOfferte/Offerta`, `ImmobiNet/Immobile`, ...)

<Note>
Best practice dichiarata da ImmobiNet: *"salva i parametri ricevuti e recupera i dati dal webservice con un processo separato"*. Quindi il webhook è una **notifica di invalidazione cache**, non trasporto dati: il receiver deve schedulare un fetch async sul metodo SOAP corrispondente. Se il PUSH non è configurabile senza intervento Rentallab, il fallback è **polling** con `getPrenotazioni(ultima-modifica=<last_sync>)` ogni 2-5 min.
</Note>
